Клиент готов платить вечером, а бухгалтер уже недоступен: сделка остывает, пока вы ждёте "нормальный" счёт из толстого клиента. Выставить счёт в 1С с телефона можно иначе: узкий HTTP-сервис в УНФ плюс тонкий UI (PWA или Telegram). Документ появляется в живой базе, PDF сразу на экране. Ниже – рабочий маршрут из пилота: расширение InvoiceBot, публикация hs, FastAPI-прокси и сценарий менеджера без ожидания бухгалтера.

Сразу разведём термины: речь про счёт на оплату, а не про счёт-фактуру и новости НДС 2026. Счёт на оплату не заменяет первичку по 402-ФЗ и сам не делает проводок – это основание для оплаты. Официальное мобильное УНФ умеет выставлять счета, но это полный клиент. Пилот заточен под один сценарий: быстро, узко, с секретами 1С на сервере.

HTTP-сервис в 1С – узкая форточка в сейф: наружу только нужная операция. API здесь – защищённый курьер между телефоном и УНФ. FastAPI-бэкенд – свой сейф с паролем 1С: браузер и бот его не видят. JSON – как акт сверки: у каждого поля своё место.

Зафиксируйте задачу: счёт клиенту без ожидания бухгалтера

Критерий успеха: за минуты на телефоне – проведённый документ в живой УНФ и PDF клиенту. Не RDP к толстому клиенту и не полное мобильное УНФ ради одной кнопки. Боль типичная: менеджер на выезде договорился о сумме, бухгалтер недоступен, сделка остывает. Десктопный путь в УНФ 3.0 знаком: Продажи → Счета покупателям → контрагент → табличная часть → провести → печать. Работает, но не из такси.

Сделайте: критерий одной фразой (документ в базе + PDF). Не делайте: смешивать счёт на оплату со счётом-фактурой в одном ТЗ.

Соберите архитектуру: PWA/Telegram → бэкенд → HTTP-сервис УНФ → PDF

Схема:
Телефон (PWA или Telegram) → код доступа → FastAPI (сейф с учёткой 1С) → HTTP Basic → InvoiceBot в УНФ → контрагент / счёт / проведение → PDF

Почему не бить телефоном напрямую в 1С? Логин и пароль базы нельзя светить в браузере и в чате бота. Бэкенд принимает X-Access-Code, а дальше сам ходит в УНФ – как охрана с ключами от сейфа, пока менеджер только показывает пропуск в приёмной.

Эндпоинты бэкенда: /api/ping, /api/counterparty, /api/nomenclature, /api/create. В УНФ: GET /ping, /counterparty, /nomenclature, /company; POST /create. URL после публикации чаще …/hs/invoicebot/…; в облаке бывает …/hs/unf – вариант публикации, не баг.

PDF в пилоте часто собирает FastAPI (ReportLab), чтобы не зависеть от печати БСП; QR оплаты – по ГОСТ ST00012. Печать средствами 1С остаётся запасным путём.

Сделайте: учётку 1С только в .env на сервере. Не делайте: вшивать логин/пароль УНФ во фронтенд или токен бота.

Установите расширение InvoiceBot и опубликуйте HTTP-сервис

Этот блок – разовая работа 1С-админа. Обещать "за вечер новичку без 1С" я не буду. После установки менеджер самообслуживается.

  1. Создайте расширение InvoiceBot (назначение "Адаптация") и снимите "Безопасный режим" – нужны файловые операции, если печать идёт через 1С.
  2. Добавьте HTTP-сервис с корневым URL invoicebot и шаблонами: GET /ping, /counterparty, /nomenclature, /company; POST /create.
  3. Вставьте модуль сервиса и пройдите все метки // ПРОВЕРИТЬ в синтакс-помощнике под вашу версию УНФ.
  4. Создайте пользователя InvoiceBot: чтение справочников + создание/проведение счетов. "Полные права" – только для пилота.
  5. Опубликуйте базу на IIS/Apache (или в облаке), включите HTTP-сервисы, отметьте InvoiceBot.
  6. Smoke-test: http://localhost/unf/hs/invoicebot/ping → JSON с ok.

Код пилота выверен по УНФ 3.0.13.374: документ СчетНаОплату, ТЧ Запасы, реквизиты Контрагент, Организация, СуммаВключаетНДС, СуммаДокумента, справочник СтавкиНДС. На УНФ 1.6 имена другие – без // ПРОВЕРИТЬ не запускайте. Для НДС 22% в базе держите актуальный релиз (в открытых гайдах для УНФ 3.0 часто порог не ниже 3.0.12.226).

GET …/hs/invoicebot/ping
Authorization: Basic <логин:пароль InvoiceBot>
→ {"ok": true, …}

createPOST: найти/создать контрагента → записать счёт → провести вне транзакции → PDF нефатален. В ответе: номер, дата, сумма, posted, pdfs. Поиск контрагента – до 7 совпадений по имени или точному ИНН.

Сделайте: сразу после публикации дерните /ping. Не делайте: открывать весь OData "на всякий случай" – узкий контракт безопаснее.

Запустите PWA/бота: код доступа, контрагент, НДС, проведение

Когда hs отвечает, поднимаете тонкий UI. Основной канал пилота – PWA (manifest + service worker, ванильный JS). Telegram на aiogram – запасной канал того же контракта.

  1. Скопируйте .env.example в .env: ONEC_BASE_URL, логин/пароль (или URL облачной публикации), ACCESS_CODE.
  2. Запустите FastAPI: Docker Compose или uvicorn (PWA обычно на :8080).
  3. С телефона введите код доступа – бэкенд дергает /api/ping до УНФ.
  4. Тип документа (счёт / акт / оба) → контрагент по имени/ИНН → позиции → НДС (22/10/7/5/0%, "в т.ч." / "сверху") → "Создать в 1С".
  5. (Опционально) Telegram-бот с whitelist ALLOWED_CHAT_IDS и командой /ping.
{
  "doc_type": "invoice",
  "counterparty": {"name": "ООО Пример", "inn": "7700000000"},
  "date": "2026-07-22",
  "vat": {"rate": 22, "included": true},
  "lines": [{"name": "Услуга", "qty": 1, "price": 10000}]
}

Для установки PWA "как приложение" желателен HTTPS; на LAN пилота часто хватает HTTP + "на главный экран" в Chrome Android. В чаты и промпты ИИ не кидайте живые ИНН, ФИО и суммы: маскируйте, пароли и ACCESS_CODE только в .env.

Смежный паттерн "тонкий канал к базе": автоматизация финансов без кода и выгрузка 1С в Excel через OData. Разборы таких связок я складываю и в Telegram "Финансист, который кодит".

Сделайте: код → /api/ping → тестовый счёт на копеечную сумму. Не делайте: пустой ALLOWED_CHAT_IDS и общий код на весь интернет как прод.

Проверьте ограничения пилота и безопасность

Акт в пилоте пока часто возвращается как счёт. Одна организация, одна база, один общий код доступа. Локальный HTTP ок для своей сети; для масштаба лучше исходящий контур, а не "весь интернет → hs".

  • Отдельный пользователь InvoiceBot, минимальные права – не "Полные права" в бою.
  • HTTPS снаружи; код доступа и пароль 1С только на сервере.
  • Whitelist chat_id для Telegram; токен бота не светить.
  • Повторная публикация после новых шаблонов/методов.
Вердикт: узкий HTTP + прокси + отдельная учётка сильнее открытого OData. Один общий access code – модель пилота, не банка. В прод – персональные коды или SSO и аудит кто выставил счёт.

Сделайте: чеклист – ping, права, HTTPS, whitelist, тестовый документ. Не делайте: публиковать hs наружу без отдельного пользователя и без кода на бэкенде.

Спланируйте, что дальше

  1. Зафиксируйте критерий: счёт в УНФ + PDF с телефона.
  2. Отдайте 1С-нику InvoiceBot и публикацию hs с проверкой /ping.
  3. Поднимите FastAPI + PWA, прогоните тестовый счёт с маскированными данными.
  4. Решите, нужен ли Telegram с whitelist.
  5. Закройте безопасность: права, HTTPS, отказ от "Полных прав" в проде.

Частые вопросы

Работает ли схема на УНФ 1.6 и 3.0?

Как идея – да. Код пилота выверен под УНФ 3.0.13.x (СчетНаОплату, ТЧ Запасы). На 1.6 пройдите все // ПРОВЕРИТЬ: имена документа, ТЧ и ставок НДС отличаются.

Нужен ли программист 1С?

На установку расширения и публикацию hs – да (или сильный админ). На ежедневный счёт с телефона – нет: менеджер работает в PWA или боте.

Можно ли только Telegram без PWA?

Да. Бот бьёт в тот же HTTP-сервис. PWA удобнее формой и PDF; Telegram – запасной канал с ALLOWED_CHAT_IDS.

Чем это лучше официального мобильного УНФ?

МП – полный клиент. Пилот – один сценарий, пароль 1С на сервере, PDF сразу. Если МП уже закрывает задачу, свой контур можно не строить.

Это про счёт-фактуру и НДС 22%?

Нет. Статья про счёт на оплату. Ставку 22% в форме учесть можно; правила счёта-фактуры с 2026 – отдельная тема.

Безопасно ли светить HTTP-сервис в интернет?

Для пилота – локальная сеть или облачная публикация хостера плюс отдельный пользователь и код на бэкенде. В прод: HTTPS, узкие права, whitelist, лучше исходящий контур.

Почему PDF иногда не из 1С?

В пилоте PDF часто собирает FastAPI (ReportLab). Документ в УНФ при этом настоящий; PDF – доставка на телефон. Печать БСП – запасной путь после сверки метаданных.
