Каждый новый чат в Cursor снова объясняете: не коммить сырые CSV, не совать ИНН в промпт, скрипты класть в scripts/. Через час агент предлагает "для удобства" залить выгрузку 1С в репозиторий. Cursor Rules для финотдела – короткий устав в файлах проекта: стиль, папки и запреты. За один вечер вы соберёте AGENTS.md и 2–3 правила .mdc, проверите Active Rules и зафиксируете отказ коммитить raw.

Rules – не "магический system prompt навсегда". Это инструкции, которые Cursor подмешивает в контекст Agent. Простыми словами: как регламент закрытия месяца, только для ИИ рядом с вашими CSV. LLM не помнит прошлые ответы; project rules добавляются в начало контекста каждый раз – так устроен продукт по документации Cursor.

Знания и промпты – в базе знаний ChatGPT/Cursor для финотдела; пилот скрипта – в Cursor: скрипт и дашборд; здесь – как закрепить правила, чтобы сырая выгрузка 1С не уезжала в чат и в git.

Поймите, зачем rules, если "и так понятно из чата"

Чат забывчив. Rules лежат в git и едут к коллеге вместе с репозиторием. Без них каждый раз заново торгуетесь с моделью про ПДн и папки – как будто каждый понедельник заново пишете регламент сверок.

Выберите формат 2026: .mdc, AGENTS.md и миграция с .cursorrules

Канон project rules – файлы .mdc в .cursor/rules/ с YAML-шапкой: description, globs, alwaysApply. Обычный .md без frontmatter система правил игнорирует. Простой старт – корневой AGENTS.md. Legacy .cursorrules лучше мигрировать в .mdc и не держать оба формата.

  • Always Apply – в каждый Agent-чат; только язык, папки, безопасность.
  • Apply Intelligently – по description, когда агент сочтёт правило релевантным.
  • globs (например **/*.py) – когда в контексте такие файлы.
  • Manual (@rule) – на старте почти не нужен.

Rules не влияют на Cursor Tab и Inline Edit – только на Agent. Держите правило короче 500 строк и дробите по зонам ответственности.

Сделайте: шаблон только на .mdc + AGENTS.md. Не делайте: заводить свежий .cursorrules по старому гайду.

Зафиксируйте каркас папок финотдела до первого правила

Пока папки не названы, агент кладёт выгрузки "куда удобно". Зафиксируйте каркас как в учёте: сырьё отдельно от очищенного среза, отчёты – отдельно от скриптов.

Workflow: выгрузка 1С → data/raw/ (.gitignore) → обезличивание → data/clean/ → scripts/ → out/

  2. В .gitignore добавьте data/raw/, .env и файлы с ПДн вне clean.
  3. ФИО, ИНН, телефоны, полные выписки – только в raw; в чат и git – никогда.
  4. Агенту давайте data/clean/ или маскированный срез – регламент в гайде по обезличиванию.
  5. Пропишите пути в always-правиле, чтобы агент не "улучшил" структуру на лету.

Сделайте: raw в gitignore до первого коммита. Не делайте: класть выгрузки 1С в корень "на пару дней".

Создайте AGENTS.md и два .mdc пошагово

Частые вопросы

Rules работают на бесплатном тарифе Cursor?

Project rules и AGENTS.md читаются из проекта. Лимиты Agent зависят от плана: сверьте cursor.com/pricing. Без Agent правила – просто текст в папке; откройте Agent и проверьте Active Rules.

Чем rules отличаются от system prompt и User Rules?

User Rules – локальные привычки в Settings на все проекты. Project rules и AGENTS.md лежат в git и шарятся с командой. System prompt модели вы не редактируете.

Нужны ли rules, если в команде один человек?

Да. Иначе каждый раз заново запрещаете коммит data/raw/. Для соло хватает AGENTS.md, always-security и .gitignore.

Сколько файлов rules достаточно в день 1?

Один AGENTS.md плюс два .mdc (security always + scripts globs). Больше десяти в первый вечер – усложняете онбординг.

Модель всё равно нарушила правило. Что делать?

Усильте формулировку ("не предлагай git add data/raw/"), продублируйте .gitignore, в чате явно @rule. Критичное смотрите в diff глазами.

Удалять ли старый .cursorrules?

После переноса в .mdc и проверки Active Rules – да. Два формата сразу делают поведение неочевидным.

Как связать rules с MCP?

В security укажите узкий path filesystem MCP и запрет секретов в mcp.json. Сначала data/clean и out, потом расширение прав.
