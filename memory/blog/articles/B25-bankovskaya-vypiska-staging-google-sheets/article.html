Банковская выписка в staging-таблицу – это слой между сырым файлом из банк-клиента и вашим ДДС/сверкой. Без него финансист копипастит строки в отчёт, ломает формулы и теряет след "откуда взялась эта сумма". Ниже – минимальный контур в Google Sheets (или Excel): колонки, импорт CSV, hash для дедупа и правило не трогать сырой файл.

Как это стыкуется с общим финконтуром – в от Excel к финконтуру за 30 дней. Если уже сверяете два CSV скриптом – сверка CSV на Python. Платёжный календарь поверх staging – календарь + n8n.

Разберите, зачем staging между банком и отчётом

Staging – как карантин на складе: товар (строки банка) сначала принимают и маркируют, потом раскладывают по полкам (статьи ДДС, статусы календаря). Прямой импорт "выписка → красивый отчёт" убивает аудит: непонятно, что пришло из банка, а что выправили руками.

Слой Что хранит Кто меняет
raw_bank_files Исходный CSV/Excel как пришёл Никто (только append новых файлов)
raw_bank (staging) Нормализованные строки + hash Импорт / скрипт
map / rules Правила контрагент → статья Финансист
dds / calendar Управленческий факт и решения Финансист после матча
Вердикт: staging обязателен, даже если у вас 50 строк в день. Не делайте: править ячейки прямо в импортированном "отчёте собственнику".

Сделайте: три зоны в одной книге – files / raw_bank / report. Не делайте: одну вкладку "Банк+ДДС+правки".

Задайте формат колонок: дата, сумма, контрагент, назначение, hash

Колонки – контракт. Пока контракт плавает, любой n8n и любая сверка будут врать. Минимум для staging:

Колонка Тип Зачем
txn_date date Дата операции банка
amount number Знак: приход > 0, расход < 0 (или amount + direction)
counterparty text Как в выписке (потом нормализуете отдельно)
purpose text Назначение платежа
account text Счёт / IBAN / краткое имя ("осн", "валюта")
src_file text Имя файла выгрузки
row_hash text Дедуп: дата|amount|purpose|account
loaded_at datetime Когда попало в staging
  1. Создайте лист raw_bank с шапкой из таблицы.
  2. Зафиксируйте знак суммы один раз на всю компанию (плюс = приход).
  3. row_hash считайте после нормализации пробелов и регистра в purpose.
  4. Не тащите в staging ИНН/карты клиентов "на всякий" – лишний ПДн-хвост.
  5. Оставьте колонку match_status: new / matched / ignored – для следующих шагов.
  6. Справочник счетов – отдельный лист accounts, не строка в каждой выгрузке как попало.
// пример ключа дедупа (псевдо)
row_hash = sha1(
  txn_date + "|" +
  amount_normalized + "|" +
  lower(trim(purpose)) + "|" +
  account
)

Сделайте: пустой raw_bank с типами колонок до первого импорта. Не делайте: "как пришло из банка – так и живём" без hash.

Импортируйте CSV/Excel и обойдите ловушки кодировки

Выписка из клиент-банка – как чемодан без бирки: вроде тот же CSV, но разделитель `;`, дата `31.07.2026`, сумма `1 234,56`, кодировка windows-1251. Google Sheets "угадывает" это с переменным успехом.

  1. Скачайте выписку в CSV или Excel и положите в папку/Drive без переименования сути периода.
  2. Импорт: Файл → Импорт → создать новый лист `import_tmp`, не вставлять в raw_bank напрямую.
  3. Проверьте кодировку: кракозябры в назначении → пересохраните UTF-8 или укажите 1251 при открытии.
  4. Даты: принудительно формат даты; текст `31.07.2026` иногда остаётся текстом – разбейте через VALUE/DATEVALUE или Apps Script.
  5. Суммы: уберите пробелы-разряды, замените запятую на точку (или наоборот под локаль Sheets).
  6. Перенесите очищенные строки в raw_bank одним блоком + src_file + loaded_at + row_hash.
Схема: файл банка → import_tmp → нормализация → append в raw_bank (только новые hash) 
Типичный чеклист после импорта:
1) число строк import_tmp = ожидаемому из банка
2) sum(amount) сходится с оборотом в PDF/клиенте
3) нет пустых txn_date
4) 0 дублей hash внутри файла

Apps Script / n8n удобны, когда выгрузка регулярная: скрипт читает CSV с Drive и дописывает raw_bank. Ручной импорт через UI – нормален на старте, пока не надоело раз в день.

Сделайте: контрольная сумма оборота после каждого импорта. Не делайте: править import_tmp и считать это staging.

Включите дедуп и правило «не трогать сырой файл»

Повторная выгрузка за тот же день – обычное дело. Без hash вы получите двойной ДДС и ложный кассовый разрыв.

  • Сырой файл в архиве/папке – read-only политика: не редактировать в Excel "чуть подчистить".
  • Перед append: антиджойн по row_hash уже лежащим в raw_bank.
  • Если банк меняет purpose задним числом – hash разъедется; заведите exception-лист, не затирайте историю.
  • Удаление строк из raw_bank – только статус ignored, не физический delete (или отдельный audit).
  • Несколько счетов: account в hash обязателен, иначе перевод между своими счетами схлопнется не туда.
  • Комиссии банка – отдельные строки staging, не "размазать" по соседнему платежу руками в отчёте.

Практика: я храню src_file как `2026-07-31_osn.csv` и раз в месяц пакую папку. Если спор "откуда цифра" – открываем файл, не спорим по памяти.

Сделайте: UNIQUE/фильтр по hash на append. Не делайте: очищать raw_bank "чтобы таблица не жирнела" без архива.

Куда вести staging дальше: ДДС, сверка, дашборд

Staging сам по себе не отчёт. Это топливо для следующих контуров:

  1. Категоризация ДДС – правила по purpose/counterparty → статья; сначала 20 правил покрывают 80% строк.
  2. Сверка – raw_bank vs учёт/1С/календарь paid; расхождения в очередь, не в молчаливый "почти ок".
  3. Платёжный календарь – matched out-строки закрывают status=paid (только с bank hash).
  4. Дашборд – читает уже категоризированный слой, не сырой staging.
  5. Алерты – n8n: новые large amount или unmatched > N часов.

Порядок внедрения, которым я пользуюсь: сначала стабильный raw_bank и контрольная сумма, потом правила статей, потом календарь/дашборд. Если начать с красивого Looker – будете красить мусор.

Разборы таких контуров – в Telegram "Финансист, который кодит".

Сделайте: DoD на сегодня – импорт одного дня + 0 дублей hash + сходимость оборота. Не делайте: сразу "ИИ разметит все статьи навсегда без проверки".

Частые вопросы

Подойдёт ли выписка из клиент-банка?

Да, это основной источник. Форматы у банков разные – поэтому и нужен import_tmp + нормализация, а не надежда на "универсальный CSV".

Как жить с несколькими счетами?

Колонка account в каждой строке и в hash. Отдельные файлы выгрузки по счетам нормальны; в staging они просто склеиваются.

Google Sheets или Excel?

Sheets удобнее для совместного доступа и n8n. Excel + Power Query отличен, если команда в Microsoft 365. Контракт колонок тот же.

Нужен ли программист?

На первом импорте – нет. Apps Script/n8n/Python подключайте, когда ручной импорт стабильно надоел и правила нормализации уже понятны.

Что делать с переводами между своими счетами?

Оставляйте в staging как есть, в ДДС помечайте как transfer / не доход. Иначе раздуете обороты.

Можно ли сразу писать в 1С?

Можно позже. Staging как раз страхует от того, чтобы сырой банк без проверки летел в учёт.

Как не утащить лишние персональные данные?

Не копируйте полные назначения с ФИО/картами в отчёты и чаты. В staging держите минимум для сверки; в дашборд – агрегаты и статьи.
