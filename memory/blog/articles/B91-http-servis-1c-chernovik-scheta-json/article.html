Сайт или CRM уже знает сумму и контрагента, а бухгалтер снова вручную бьёт счёт в 1С - это лишний день и риск ошибки в реквизитах. HTTP-сервис решает узкую задачу: ваше приложение шлёт POST с JSON, 1С создаёт черновик счёта на оплату и возвращает номер в ответе. Ниже - маршрут для финотдела: контракт JSON, свой сервис или готовое расширение для БП, безопасность и проверка через curl без копипаста в интерфейсе.

Сразу разведём термины: речь про счёт на оплату, а не про счёт-фактуру, НДС 2026 и Sber API DirectBank. Счёт на оплату - основание для оплаты; бухгалтер сверяет его в разделе "Продажи → Счета покупателям". HTTP-сервис - узкая форточка в сейф 1С: наружу только нужная операция. JSON - как структурированный акт сверки: у каждого поля своё место. API здесь - защищённый курьер между вашим backend и базой.

Если вам нужен только счёт с телефона через УНФ - это другой сценарий (PWA/Telegram). Если достаточно read-only остатков в Cursor - смотрите MCP, а не POST документов. Здесь - цепочка "ваше приложение → POST JSON → черновик в 1С".

Оцените, когда HTTP-сервис нужен финотделу (и когда нет)

Задача появляется, когда счёт рождается вне 1С: интернет-магазин, CRM, собственный портал заявок, no-code backend. Ручной ввод работает при десятке счетов в месяц. При сотнях - ошибки в ИНН, суммах и дубли заказов съедают время контролёра.

Критерий Ручной счёт в 1С OData / MCP read-only HTTP POST → черновик
Задача Разовые продажи Отчёты, остатки, выгрузки Создать счёт из внешней системы
Кто инициирует Бухгалтер/менеджер в UI Аналитик, fin-ассистент Сайт, CRM, свой сервис
Риск Человеческая опечатка Чтение без записи Нужны права и auth на запись
Когда выбирать Мало документов Только чтение данных Узкий сценарий "создать счёт"
Правило выбора: если нужно только читать остатки - не открывайте POST на создание документов. Если в Бухгалтерии 3.0 и хватает готового REST - сначала оцените расширение bit_http_api, прежде чем писать свой обработчик.

Сделайте: сформулируйте критерий успеха одной фразой: "POST из приложения → черновик счёта → номер в JSON-ответе". Не делайте: смешивать счёт на оплату со счётом-фактурой в одном ТЗ.

Подготовьте JSON-контракт и закройте риски по данным

До кода зафиксируйте поля, которые шлёт внешняя система. Минимум: идентификаторы продавца и покупателя (ИНН или GUID в справочнике), массив позиций с наименованием, количеством и ценой, опционально comment как ID заказа с сайта. Договоритесь о единицах: в готовом REST bit_http_api поле price передаётся в копейках (1 000 000 = 10 000,00 ₽) - ошибка здесь даёт счёт в 100 раз больше или меньше.

Пример тела для обмена (маскированные данные):

{
  "seller_inn": "7700000000",
  "payer_inn": "7700000001",
  "comment": "ORDER-2026-001",
  "items": [
    {"name": "Консультация", "qty": 1, "price": 1500000}
  ]
}

Безопасность до публикации: отдельный пользователь 1С с минимальными правами (создание счетов + чтение контрагентов и номенклатуры), Basic Auth или токен в заголовке, только HTTPS, лимит размера тела. Токены не передавайте в query URL. При отладке JSON не заливайте живые ИНН, ФИО и суммы в облачный ChatGPT - маскируйте, как в гайде по обезличиванию для финансиста.

Сделайте: таблицу полей JSON с типами и примерами для разработчика и бухгалтера. Не делайте: отдавать учётку с полными правами "на время теста".

Настройте HTTP-сервис: свой код или готовое расширение

Схема:
Ваше приложение → POST + Content-Type: application/json → HTTPS + auth → HTTP-сервис 1С → черновик "Счёт покупателю" → JSON с number, id, date

Две рабочие ветки. Ветка A - свой HTTP-сервис (любая конфигурация с поддержкой HTTP-сервисов платформы):

  1. В конфигураторе: "Общие → HTTP-сервисы" - корневой URL, шаблон /invoices (или /create), метод POST, обработчик на встроенном языке.
  2. В обработчике: ТелоЗапроса = Запрос.ПолучитьТелоКакСтроку() → ЧтениеJSON/ПрочитатьJSON → проверка полей → создание документа без проведения (черновик) → ЗаписьJSON в HTTPСервисОтвет(200) с number, id, date.
  3. Опубликуйте базу на IIS или Apache, включите HTTP-сервисы в мастере публикации. URL вида https://host/{публикация}/hs/{имя_сервиса}/{шаблон}.
  4. Создайте пользователя API с минимальными правами, проверьте smoke-test POST на тестовом JSON.

Ветка B - bit_http_api для 1С:Бухгалтерия 3.0 (конфигурация 3.0.190.22+, роль bitHttpApi_ОсновнаяРоль): готовый endpoint POST /hs/bit_http_api/invoices с Basic Auth. Успешный ответ включает id, number, date, total_amount, comment - их сверяют в UI 1С.

Параметр Свой HTTP-сервис bit_http_api (БП 3.0)
Когда Нестандартная конфигурация, свой контракт Типовая Бухгалтерия, нужен REST быстро
Трудозатраты 1С-разработчик + тесты Установка расширения + публикация
Черновик Явно без проведения в коде Зависит от настроек расширения
Безопасность Проектируете сами Basic Auth + узкий REST vs OData

На неверный ввод платформа и практика рекомендуют код 400, на отсутствие маршрута - 404, на auth - 401/403. Не прячьте ошибки бизнес-логики в HTTP 200 с текстом "ошибка".

curl -X POST "https://host/base/hs/myapi/invoices" \
  -H "Content-Type: application/json" \
  -u api_user:*** \
  -d '{"seller_inn":"7700000000","payer_inn":"7700000001","items":[{"name":"Услуга","qty":1,"price":100000}]}'

Сделайте: на пилоте создавайте только черновик без проведения - бухгалтер успеет проверить. Не делайте: на первом запуске сразу проводить документ и слать PDF клиенту.

Проверьте результат и разберите типичные ошибки

После POST откройте "Продажи → Счета покупателям": контрагент, сумма, комментарий с ID заказа. Сверьте номер из JSON-ответа с карточкой в списке. Негативные кейсы прогоняйте сразу: пустое тело → 400, неверный ИНН → 4xx или 500 с записью в журнал регистрации 1С.

  1. Smoke-test GET health или POST на минимальном JSON с тестовыми ИНН.
  2. Проверьте 404: неверный шаблон URL - платформа вернёт Not Found, если маршрут не совпал.
  3. Типичная 500 при POST счёта - контрагент не найден по ИНН или битый JSON; смотрите журнал регистрации, а не только ответ curl.
  4. Зафиксируйте в runbook: что логировать снаружи (без ПДн), что - только внутри 1С.

Если URL после публикации не открывается - перепроверьте галку HTTP-сервисов и имя публикации. Повторная публикация нужна после каждого нового шаблона или метода.

Сделайте: чеклист "curl → номер в ответе → документ в списке → сумма совпала". Не делайте: считать интеграцию готовой после одного успешного POST без негативных тестов.

Спланируйте, что автоматизировать дальше

Черновик - сознательный первый шаг. Отдельно, после стабильного POST, добавляют проведение, печать PDF, отправку в ЭДО, webhook статуса оплаты из банка. Смежные сценарии без dev-команды - в материале про автоматизацию финансов без кода.

  1. Зафиксируйте JSON-контракт и единицы цены (рубли vs копейки).
  2. Выберите ветку: свой hs или bit_http_api для БП.
  3. Опубликуйте hs, прогоните curl/Postman с маскированными данными.
  4. Сверьте документ в "Счета покупателям" и закройте негативные кейсы.
  5. Решите, нужны ли проведение и PDF на втором этапе.

Частые вопросы

Можно ли настроить POST счёта без программиста?

Готовое расширение bit_http_api для Бухгалтерии 3.0 ставит 1С-админ: публикация hs и Basic Auth. Свой HTTP-сервис под нестандартную конфигурацию - задача 1С-разработчика; финансист задаёт JSON-контракт и критерии приёмки.

Сколько займёт внедрение?

Готовый REST на типовой БП - от нескольких часов на установку и тесты. Кастомный обработчик - от пары дней на разработку и сверку имён документов в вашей конфигурации. Заложите время на негативные тесты и согласование единиц цены.

Какие риски для данных и 152-ФЗ?

POST несёт коммерческие реквизиты: ИНН, суммы, наименования. Используйте HTTPS, отдельного пользователя API, не логируйте тело запроса в открытые системы. При отладке маскируйте ПДн; сырые JSON не отправляйте в облачные LLM.

Чем POST-счёт отличается от OData и MCP?

OData и MCP read-only подходят для чтения остатков и отчётов. HTTP POST создаёт документ в базе. Не открывайте широкий OData "на запись", если нужен один сценарий - узкий endpoint безопаснее.

Почему в ответе 500, хотя JSON валидный?

Частая причина - контрагент не найден по ИНН или номенклатура не сопоставилась. Откройте журнал регистрации 1С, сверьте справочники. Проверьте, что seller_inn и payer_inn есть в базе до POST.

Нужно ли сразу проводить счёт из API?

На пилоте - нет. Создавайте черновик без проведения, пусть бухгалтер проверит суммы и НДС. Проведение, PDF и ЭДО добавляют отдельным этапом после стабильных тестов.

Работает ли это для УНФ и других конфигураций?

HTTP-сервисы - механизм платформы 1С; имена документов и реквизитов зависят от конфигурации. Для УНФ и ERP сверьте объект "Счёт на оплату" с синтакс-помощником. bit_http_api заточен под Бухгалтерию 3.0.
