Финотдел тратит по полчаса в день на обход кабинета ЭДО: где УПД висит на подписи контрагента, что уже можно ставить в оплату, что отклонили. При пятнадцати исходящих документах в день и трёх отделах ручной мониторинг ломается. Ниже соберёте живой реестр статусов в Google Sheets с автообновлением через API оператора или n8n – без ежедневного входа в ЭДО и без программиста на постоянке.

ЭДО (электронный документооборот) – обмен УПД и счетами-фактурами через оператора: Диадок, СБИС и др. Статус "отправлен" в кабинете и "готово к оплате" в регламенте – разные вещи. Google Sheets здесь лёгкий дашборд для финдира и закупок, не замена 1С. С 1 января 2026 для организаций на ЭДО обязателен формат УПД 5.03; электронные ТОРГ-12 через операторов больше не ходят.

API оператора – как защищённый курьер между кабинетом ЭДО и таблицей: приносит метаданные (номер, дата, статус подписи), без тел документов. JSON в ответе – как структурированный акт сверки с именованными полями. Про хранение ключей и триггеры – в гайде по кнопке "Обновить данные"; про no-code маршруты – в автоматизации финансов без кода.

Оцените, нужен ли реестр статусов ЭДО в Google Sheets

Сделайте реестр, если в день от пяти до пятнадцати документов, статусами пользуются закупки и бухгалтерия, а в 1С нет модуля ЭДО с выгрузкой. Не делайте, если СЭД или 1С уже синхронизирует статусы. Не делайте полный API-контур без доступа к API оператора – останется CSV-импорт раз в неделю (до тридцати документов).

Маршрут Когда выбирать Минус
Apps Script + API Диадок Есть client_id, нулевой хостинг Настройка OAuth и маппинга
n8n / Make + HTTP Есть no-code контур, нужны алерты Отдельный сервер n8n
CSV с Drive + скрипт Малый объём, нет API Задержка, ручной экспорт
Вердикт: с API Диадок начинайте с GetDocflowEvents – эффективнее перебора всей очереди. Без API хватит CSV раз в неделю.

Подготовьте staging-лист и защитите данные от утечки

Разделите два слоя статусов. Внешний слой – что вернул API: отправлен, доставлен, ожидает подписи контрагента, подписан обеими сторонами, отклонён. Внутренний слой – бизнес-смысл: "на проверке закупок", "готово к оплате". Поле DocflowStatus в API – не синоним "можно платить". Зафиксируйте пять–семь формулировок без двусмысленности.

Создайте лист edo_status с колонками: doc_id (MessageId + EntityId или номер УПД), counterparty_inn, doc_type, doc_date, amount, api_status_raw, business_status, last_event_at, updated_at, alert_flag. Отдельный лист log – для ошибок API (401, 402, таймауты), чтобы сбой одного запроса не ломал весь реестр. На листе status_map сведите коды API к business_status – финансисты читают второй столбец, не сырые enum.

Безопасность: токены access_token, client_id и boxId храните только в Script Properties, не в ячейках. Не отправляйте реестр с реальными ИНН и суммами в ChatGPT или Claude – маскируйте идентификаторы; чеклист – в гайде по обезличиванию. Доступ к таблице по ролям: закупки видят статусы, редактор скрипта – один человек. Сделайте: status_map и log. Не делайте: копировать тексты УПД в Drive "для сверки".

Настройте автообновление: Apps Script, n8n или CSV

Маршрут A: Apps Script + API Диадок. Логика та же для СБИС, меняются URL и поля.

Схема: триггер → POST GetDocflowEvents (cursor AfterIndexKey) → mapStatus → upsertRow в edo_status → log при ошибке
  1. Зарегистрируйте интеграцию в Кабинете интегратора Диадок, получите client_id и access_token в Properties.
  2. Создайте bound-скрипт (Расширения → Apps Script): fetchDocflowEvents_, mapStatus_, upsertRow_.
  3. Сохраняйте AfterIndexKey в Properties после каждого опроса – забираете только новые события.
  4. Запрашивайте метаданные без тел документов (лимит ответа GetDocflowEvents – 1 048 576 байт).
  5. Маппинг: WaitingForRecipientSignature → "ожидает подписи"; DocflowStatus Finished → "подписано обеими"; отказ → "отклонён".
  6. Upsert по doc_id – обновление api_status_raw, business_status, last_event_at или новая строка.
  7. Триггер everyHours(1) или 2–4 раза в день. Лимиты: UrlFetch 20 000/день, runtime 6 мин/запуск.
function fetchDocflowEvents_() {
  var props = PropertiesService.getScriptProperties();
  var resp = UrlFetchApp.fetch(
    'https://diadoc-api.kontur.ru/V4/GetDocflowEvents',
    {
      method: 'post',
      contentType: 'application/json',
      headers: { Authorization: 'Bearer ' + props.getProperty('DIADOC_TOKEN') },
      payload: JSON.stringify({ AfterIndexKey: props.getProperty('AFTER_INDEX_KEY') || '' }),
      muteHttpExceptions: true
    }
  );
  if (resp.getResponseCode() !== 200) { logError_(resp.getResponseCode()); return []; }
  var data = JSON.parse(resp.getContentText());
  if (data.AfterIndexKey) props.setProperty('AFTER_INDEX_KEY', data.AfterIndexKey);
  return data.Events || [];
}

function mapStatus_(event) {
  var r = event.Document || {};
  if (r.RecipientResponseStatus === 'WaitingForRecipientSignature') return 'ожидает подписи контрагента';
  if (r.DocflowStatus === 'Finished') return 'подписано обеими сторонами';
  if (r.RecipientResponseStatus === 'RecipientSignatureRequestRejected') return 'отклонён';
  return 'отправлен';
}

Маршрут B (n8n / Make): HTTP Request к API оператора по cron → нода Google Sheets Update Row (search по doc_id, иначе Append). Паттерн как у шаблонов Diadoc→Sheets. Опционально Telegram при "отклонён" или если "ожидает подписи" дольше N дней – тот же канал, что в Telegram "Финансист, который кодит".

Маршрут C (полуавтомат): еженедельный экспорт списка документов из кабинета ЭДО (CSV) в папку Drive → Apps Script Utilities.parseCsv() → merge в edo_status. Подходит до ~30 документов в неделю без API. Сделайте: один успешный ручной запуск syncEdoStatuses до триггера. Не делайте: Bearer-токен в ячейке A1 "временно".

Проверьте реестр и разберите типичные ошибки

Первую неделю сверьте десять строк edo_status с кабинетом ЭДО. Отдельно кейс "подписано нами ≠ подписано обеими".

Код / симптом Причина Что сделать
401 Просроченный токен Обновить access_token в Properties
402 Нет подписки на API Продлить тариф; fallback на CSV
403 Нет прав к ящику Проверить boxId и роли
Дубликаты Нет upsert по doc_id Ключ MessageId+EntityId
Статус не меняется GetDocuments вместо Events GetDocflowEvents + cursor

Журнал log должен писать код ответа и время, но не ронять весь сценарий при одной ошибке. При недоступности API ставьте alert_flag в строке документа – финансист видит маркер в таблице. Сделайте: чеклист из десяти документов на первую неделю и правило эскалации при 402. Не делайте: считать строку в Sheets юридическим источником истины – первичен кабинет оператора ЭДО.

Расширьте автоматизацию: алерты и следующие шаги

Когда реестр стабилен, добавьте алерт в Telegram при "отклонён" или просрочке подписи (больше пяти рабочих дней в "ожидает контрагента"). Свяжите business_status "готово к оплате" с очередью согласования – но только после внутренней проверки закупок, не по одному API-полю.

При росте объёма (сотни документов в день) опрос идёт через события GetDocflowEvents, а не полный перебор GetDocuments – тот возвращает не более 100 документов за запрос, при большем объёме нужна пагинация AfterIndexKey. В 2026 операторы двигаются к универсальным сообщениям ЭДО – следите, что форматы УПД 5.03 поддерживаются; реестр статусов не заменяет проверку формата.

Пошаговый разбор маппинга и триггеров с обратной связью – в закрытом клубе KODA, где разбираем рабочие таблицы финотдела на живых примерах.

Частые вопросы

Можно ли собрать реестр без программиста?

Да, для малого объёма: еженедельный CSV из кабинета ЭДО и Apps Script по шаблону выше. API Диадок требует однократной регистрации интеграции – это может сделать IT или подрядчик за один вечер. n8n настраивается без кода, но нужен OAuth к API и Google Sheets.

Сколько времени займёт внедрение?

Staging-лист и полуавтомат с CSV – один вечер. GetDocflowEvents с триггером и маппингом – от одного до трёх дней с тестовой сверкой десяти документов. Заложите согласование словаря статусов с закупками – без этого таблица превращается в "ещё один файл".

Какие риски для персональных и коммерческих данных?

Токены API, облако Google и доступы к таблице. Не храните секреты в ячейках, не скидывайте реестр с ИНН в LLM. Ограничьте sharing: только домен компании. Подробнее – в материале про обезличивание.

Работает ли со СБИС?

Та же логика: API → маппинг → upsert. Пример Диадок – лучше документирован. Перенесите status_map под справочник оператора.

Чем лучше модуля ЭДО в 1С?

Sheets – дашборд без доработки 1С. Проводки остаются в учётке; реестр закрывает "где документ по подписи".

Как не перепутать "подписано нами" и "подписано обеими"?

Разные business_status и правило: оплата после "подписано обеими". Смотрите SenderSignatureStatus, RecipientResponseStatus и DocflowStatus.

Что если API вернул 402?

Продлите подписку на API. До этого – CSV-экспорт и запись в log.
